# D09-B scenario matrix — concurrency, recovery and transactional security

| Canonical scenario | Existing implementation | Test needed | Gap/fix |
|---|---|---|---|
| T035/T036 concurrent roster commit, same key and payload | `RosterService.commitRosterImport` uses a canonical payload digest, a natural `CommandLedgerEntry` key, a transaction, and enrollment `personKey` uniqueness | Concurrent real PostgreSQL requests; assert one enrollment, ledger and audit, and replay of the committed response after the losing request observes the unique race | Handle the post-commit/unique-race path by reading the authoritative ledger and replaying the matching digest |
| T035/T036 same key with changed payload | D09-A compares the full canonical normalized payload and returns `409 IDEMPOTENCY_KEY_REUSED` on an existing committed ledger | Concurrent requests with different canonical rows and one shared key; assert exactly one digest wins and the other conflicts | Preserve the winner and translate the losing race to the same canonical conflict |
| T035 duplicate logical identity with different keys | DB schema has `@@unique([tournamentId, personKey])`; service also prechecks inside the transaction | Concurrent requests with different keys and one `personKey`; assert one durable enrollment and a safe duplicate conflict | Keep the DB uniqueness fence; map only a completed idempotent winner to replay, leave different-key duplicate as `DUPLICATE_PERSON_KEY` |
| T035 worker crash before commit / T035 retry after ambiguous response | Import work is one Prisma transaction; D09-A ledger and audit are in that transaction | Fault-injected transaction rollback and commit-then-throw retry; assert no partial rows before commit and replay after commit | Add explicit ambiguous-outcome replay recovery around the transaction boundary |
| T038 activation token claim race | Claim is transactional and claim ledger has a natural command key; token is consumed in the same transaction | Concurrent claims using the same raw token; assert one user/enrollment/claim/audit and a safe loser/replay | Translate a unique-race loser to the durable claim replay when available |
| T038 staff invitation acceptance race | Invitation and assignment are changed in one transaction, but acceptance update was unconditional | Concurrent accepts; assert one state transition, one assignment and one audit, with safe replay for the loser | Use a conditional state update (`INVITED` → `ACTIVE`) and return replay when the conditional update loses |
| T039 recovery token consume race | Conditional `updateMany` fences token consumption; credential/session/audit writes share the transaction | Concurrent token consumption and injected credential failure | Existing conditional consume/rollback is covered; add focused concurrent and privacy assertions |
| BR-41/BR-42 audit consistency/privacy under failure | Audit records are written inside relevant transactions and omit raw secrets | Rollback and race tests count durable audit rows and scan for token/password/hash/source | Verify no audit side effect survives a failed transaction and no secret appears in durable evidence |

This matrix is intentionally limited to D09-B scenarios and the D04–D08 services they exercise. D09-A idempotency behavior is reused as the oracle; it is not re-audited here.
