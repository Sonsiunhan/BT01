## D12-F01 — FIXED / VERIFIED

### Original reproduction

A `TOURNAMENT_ADMIN` could supply a foreign `tournamentId` to the roster list endpoint. The route checked only the role and `RosterService.listEnrollments()` queried enrollments directly by that ID.

### Root cause

The list operation did not resolve the tournament's authoritative contract and did not check the caller's active `TournamentContractTaBinding` before querying enrollment data.

### Production change

- Added the shared roster contract-scope authorization helper.
- Applied it to roster listing and existing activation authorization paths.
- Roster listing now resolves the tournament contract, requires an active binding for `TOURNAMENT_ADMIN`, allows `SYSTEM_ADMIN`, and rejects non-admin actors before `findMany`.
- Missing or malformed IDs return `404` without enrollment data.

### Authorization evidence

- Bound TA → own tournament: allowed.
- Bound TA → same broader test scope but foreign contract/tournament: denied `403`.
- Bound TA → foreign test tenant/contract/tournament: denied `403`.
- Unbound TA, participant/user, referee, staff, guest: denied `403`.
- System Admin → representative tournament: allowed.
- Nonexistent/malformed tournament ID: `404`, no enrollment data.
- Denied reads caused no enrollment, command-ledger, or audit mutation.

## D12-F06 — FIXED / VERIFIED

### Original reproduction

`ActivationService` derived its expiry from `CANDIDATE_POLICY_DEFAULTS_V1.claimTokenTtlHours`, whose runtime value was `168` hours.

### Root cause

The approved 24-hour policy had not replaced the shared contract default, so the production service correctly consumed an incorrect shared value.

### Production change

- Changed the shared candidate policy default from `168` to `24` hours.
- `ActivationService` continues to derive its runtime expiry from that shared source of truth.
- No schema or migration change was made.

This is a minimal shared-contract change and requires **SHARED CONTRACT CHANGE — LONG REVIEW REQUIRED**.

### Boundary and lifecycle evidence

- Token before expiry: valid.
- Token at exact expiry: rejected with `TOKEN_EXPIRED`.
- Token after expiry: rejected with `TOKEN_EXPIRED`.
- Claim replay remains idempotent and does not create a second account.
- Existing one-time claim, credential, account binding, and token-hash behavior remains covered by the activation regression suite.
- Raw token was not present in the command ledger or audit records.
