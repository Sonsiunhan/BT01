## Verified behavior

1. The real SYSTEM_ADMIN account logged in and loaded the P09 TA table.
2. The TA uploaded a canonical CSV, saw one valid preview row, committed it, and double-submitted the commit control. The durable roster contained exactly the seeded participant plus one `D10C:NEW-001` row.
3. The TA issued activation for the imported row. The one-time raw handoff was shown only in the current UI handoff and was not stored in browser storage.
4. The participant claimed the imported identity, set credentials, and replayed the claim token. Replay returned the idempotent claimed step and did not create another account or credential ledger entry.
5. The TA invited the referee; the referee accepted from a separate browser context; the TA then revoked the assignment. The accepted and revoked states were visible from their authoritative pages.
6. The participant requested recovery; the admin took ownership, recorded a verification reference, issued a reset handoff, and the participant set a new password. The reset handoff was absent from local/session storage.
7. The participant acknowledged the currently published regulation version. The P18 page showed version `1` and the satisfied state.
8. A participant navigating directly to the TA roster route received the server authorization boundary and no TA page.

## Scoped fix found by the real browser path

The existing tournament staff API used raw `fetch` without the required `X-OTT-Request` CSRF header and sent `Content-Type: application/json` on bodyless POST decisions. The browser test exposed both boundaries. `tournamentStaffApi` now sends the CSRF header and only sends a JSON content type when a body exists; this preserves the server's CSRF contract and allows invitation accept/revoke requests to complete through the real HTTP path.

No commit was created and no remote operation was performed.
