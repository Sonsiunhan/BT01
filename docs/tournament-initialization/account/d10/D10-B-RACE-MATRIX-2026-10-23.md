# D10-B race and failure matrix

| Race/failure | Authoritative state | Expected invariant | Current protection | D10-B proof | Gap/fix |
|---|---|---|---|---|---|
| Two `startRunning` calls for one tournament | `TournamentStateStore` projection plus `Tournament` row | One transition, one success audit; losers see the canonical blocked state | Per-process `withLock`; PostgreSQL serializable transaction; conditional status/revision update | Unit race (8 calls) and PostgreSQL concurrent start (3 calls) | Fixed cross-process boundary with `PrismaTournamentStartTransaction` and CAS update |
| ACK check while config version changes | `Tournament.activeConfigVersionId` and immutable config-version row | Only the exact active version can authorize start | ACK guard checks tournament/version/enrollment in one serializable transaction | PostgreSQL ACK/version race; D10-A exact/stale guard tests | No second ACK system; fail closed on stale version |
| Start versus referee accept/revoke/expiry | `TournamentStaffAssignmentRecord.status` scoped by tournament | Only `ACTIVE` referee state at the transition boundary counts | Prisma readiness query; staff terminal updates are conditional | PostgreSQL start/revoke and concurrent accept tests; unit revoke-during-ACK regression | Shared transaction-scoped advisory lock plus final readiness revalidation |
| Participant/admission state | Enrollment rows scoped by tournament and contract | Eligible linked accounts are counted; foreign/unclaimed rows cannot satisfy readiness | `PrismaReadinessSourcesAdapter` reads inside the lifecycle transaction | PostgreSQL final-state assertions and foreign-scope rejection | No roster/import redesign; lifecycle consumes existing D03-D09 authority |
| Failure before commit | DB lifecycle row, projection, audit | No status change and no success audit | Staged projection; transaction rollback | Injected failure before commit | Restores memory projection and audit length |
| Failure inside transaction | DB lifecycle row and audit row | Durable status/audit roll back together | Same serializable transaction | PostgreSQL rollback test | No partial durable success |
| Commit succeeds but response is lost | DB row is authoritative; projection must converge | Retry cannot duplicate transition or audit | Explicit committed/lost-response fault boundary; retry sees `RUNNING` | PostgreSQL ambiguous-response test | Literal process kill was not claimed; deterministic post-commit response loss was simulated |
| Serialization conflict (`P2034`) | DB transaction snapshot | Retry re-enters all authority checks | Bounded three-attempt retry | PostgreSQL injected P2034 test | Permanent authorization/readiness errors are not retried |
| Foreign ACK/referee/tenant state | Tournament + contract composite scope | State from another scope never satisfies readiness | Composite filters and version/tournament checks | PostgreSQL foreign-scope test | No cross-scope fallback |
| Audit/privacy under races | `TournamentAuditLogRecord` and sanitizing audit projection | One success evidence; no secrets or unnecessary PII | Audit writes inside lifecycle transaction; existing sanitization | D10-A privacy flow plus D10-B audit counts | Raw tokens/passwords/hashes are not written |

The lifecycle transition depends on participant eligibility and active referee counts, so those reads are part of the transaction boundary. Admission command idempotency remains the D09 authority and was regression-tested separately; this slice does not redesign roster/import.
