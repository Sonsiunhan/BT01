# D10-B — Cross-stream concurrency and transaction integrity

## Outcome

D10-B is implemented on `duc-tournament` as uncommitted work. The real weakness was a cross-store time-of-check/time-of-use window: lifecycle readiness was read from PostgreSQL, then an ACK check awaited, and the in-memory lifecycle transition committed without a final readiness recheck or a shared lock with referee mutations.

## Fixes

- Added `PrismaTournamentStartTransaction`, a serializable PostgreSQL transaction with a transaction-scoped advisory lock per tournament and bounded `P2034` retry.
- The lifecycle transaction conditionally updates the durable `Tournament` row by status and revision and writes `TOURNAMENT_STARTED` audit evidence in the same transaction.
- `PrismaReadinessSourcesAdapter` and the ACK guard accept the current transaction client, so participant/referee/ACK checks share the lifecycle snapshot.
- `startRunning` revalidates readiness after ACK validation and stages the in-memory projection until the durable transaction commits. Rollback restores the prior projection and audit length; an explicitly marked post-commit lost response retains the committed projection for safe retry.
- Staff accept, revoke and invitation-expiry transactions acquire the same advisory lock. Their existing conditional state transitions and idempotent audit behavior remain intact.

## Verified behavior

The disposable PostgreSQL suite (`scripts/d10b-isolated-db.mjs`, PostgreSQL 18 on `127.0.0.1`) passed 9/9 tests:

1. Three concurrent `startRunning` requests produced one `RUNNING` transition, one durable success audit and two canonical losers.
2. An injected `P2034` caused a bounded retry that re-entered authoritative validation and produced one transition/audit.
3. Start versus referee revoke was ordered by the shared advisory lock; the final state was either a valid start before revoke or a blocked start after revoke, never a start based on stale `ACTIVE` readiness.
4. A config-version update racing start failed closed with stale-version semantics when it won the boundary; if start won, it committed against the version validated at that boundary.
5. A pre-commit fault rolled back the durable tournament status and audit and left the in-memory state `APPROVED`.
6. A deterministic response loss after durable commit replayed without a duplicate transition or audit.
7. Foreign referee state did not satisfy the target tournament's lifecycle gate.
8. A foreign-tournament ACK did not satisfy a locally ready tournament.
9. Concurrent referee acceptance yielded one terminal `ACTIVE` assignment and one acceptance audit.

Focused in-memory D10-B tests passed 4/4, including the original revoke-during-ACK regression, concurrent starts, rollback and marked post-commit response loss. D10-A focused guard tests passed 3/3; its real PostgreSQL runner passed. L10 passed 1/1. D06 staff unit regression passed 15/15. D09-B PostgreSQL regression passed 5/5 after the shared staff-lock change.

## Transaction and audit boundaries

The database row update and durable success audit are atomic. The process-local tournament/audit projection is applied only after transaction success; a failed transaction cannot leave a `RUNNING` projection. The post-commit response-loss test is a deterministic wrapper around a successful commit and is not a literal process termination claim.

Audit evidence contains lifecycle snapshots and scope identifiers only. The D10-A privacy flow continues to assert that activation tokens and password text are absent; D10-B adds no raw token, password, credential hash or unnecessary PII.
