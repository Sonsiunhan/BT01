### D11-F04 - P1 - scoped Tournament Admin audit access is denied

Verdict: VERIFIED FINDING.

Actor/precondition: a persisted TOURNAMENT_ADMIN was bound to Unit A's active
contract. Reproduction: request the real audit endpoint for the bound Unit A
target and also request the unfiltered endpoint. Expected: canonical scoped
audit access for the own tournament/scope. Actual/API result: both requests
returned 403; SYSTEM_ADMIN returned 200 and unrelated actors were denied.
Security impact: the scoped administrator cannot perform the required audit
review, while this is not an over-disclosure path.

The canonical S08 acceptance/design requires `ADMIN` or
`TOURNAMENT_ADMIN` for the capability boundary, and the P14 requirement is a
permission-aware audit view. The authoritative audit route uses
`assertAdminActor`, which accepts only the `ADMIN` role. A real TOURNAMENT_ADMIN
with an active contract/unit binding received 403 even for its own target.

Owner/boundary: Long/shared server authorization and audit route; Son owns the
P14 UI integration. Minimal follow-up point: the server permission predicate
and its shared role/capability contract, without rewriting the audit page.

### D11-F09 - P1 - token-like audit reason is not sanitized

Verdict: VERIFIED FINDING.

Actor/precondition: SYSTEM_ADMIN read the real audit endpoint after a contract
status update containing the deterministic sentinel. Expected: audit payloads
contain no token-like material. Actual/API result: the response exposed the
sentinel in `reason`; raw password, Bot source, and diagnostics were absent.
Security/privacy impact: a real bearer/recovery/invitation token placed in a
reason could be persisted and disclosed to an authorized audit reader.

The disposable setup submitted a non-secret, deterministic Bearer-shaped
sentinel as a contract status reason. The real P14 response contained that value in the
audit `reason` field. Password-like values, Bot source, and diagnostic markers
were absent, but the audit sanitizer covers snapshots and does not sanitize
the separate reason string. A real token-like value could therefore be
persisted and returned by the audit endpoint.

Owner/boundary: Long/shared server audit service and route. Minimal follow-up
point: sanitize or reject sensitive reason material at the audit port/service;
the P14 viewer should continue to consume the sanitized authoritative payload.

### D11-F03 - P1 - Offline capability failure is fail-open

Verdict: VERIFIED FINDING.

Actor/precondition: a persisted PLAYER opened P15; the capability endpoint was
also queried with persisted SYSTEM_ADMIN, TOURNAMENT_ADMIN, PLAYER, REFEREE,
Guest, and unauthenticated sessions. Reproduction: open `/admin/offline`, then
repeat with a delayed capability response and an injected 503. Expected: the
Hub remains denied/unavailable until authoritative capability data is resolved.
Actual: all four protected actions remained visible and the runtime was shown
as `READY`. API result: real server 403 for the non-admin actors; the browser's
current client path observed a real 404/network failure and converted it to the
same permissive fallback.

The real API returned 403 for non-admin actors. In the real browser, the
frontend requested `/admin/offline/capabilities` while the authoritative server
route is `/api/admin/offline/capabilities`; the resulting real 404/network
failure was caught by `offlineApi.ts`, which returned all capabilities true and
runtime `READY`. The Hub then rendered all four protected actions for a
PLAYER. A delayed unresolved capability request also rendered the four actions
while loading. An injected 503 produced the same permissive READY fallback.

Expected behavior is fail-closed: unresolved, denied, unavailable, or invalid
capability authority must not expose protected actions or claim runtime
readiness. Security impact: a denied or unavailable Offline capability can
appear authorized, expose protected navigation, and claim runtime readiness.
The server API and client path/fallback are separate integration
points and both must be corrected together.

Owner/boundary: Son owns the Offline UI/client adapter; Long owns the
authoritative capability route and shared permission contract. Minimal follow-up
point: one capability client/route contract with explicit denied/unavailable
states; do not duplicate server authorization in the browser.

### D11-F05 - P2 - Offline Bot error has no Retry action

Verdict: VERIFIED FINDING.

Actor/precondition: a persisted SYSTEM_ADMIN opened the real P15 Bot page; only
the Bot-library GET was intercepted with a deterministic 503 UI failure.
Expected: an accessible error plus an explicit Retry recovery action. Actual:
the error alert rendered, but no Retry/`Thử lại` action was present. API result:
the real Bot-library authorization/privacy probes passed; the 503 is explicitly
browser UI-state evidence. Impact: a transient Bot-library outage leaves the
user without the canonical recovery path.

With a real authenticated browser session and only the Bot-library GET failure
injected, the Bot page showed an accessible error alert but no `Retry`/`Thử
lại` action. The page's existing reset/new-match action is not recovery for a
failed library request. This violates the BA/SA page rule requiring recoverable
error states where retry is meaningful.

Owner/boundary: Son, P15 Bot UI. Minimal follow-up point: retry the failed
library load while preserving the safe error state.
